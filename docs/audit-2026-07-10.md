# Cuboidy 仕様・実装監査レポート (2026-07-10)

## 1. 概要

Cuboidy v0.8 draft の仕様、TypeScript core/CLI、Web エディタ、JSON Schema、
サンプルモデル、テスト構成を横断して監査した。

結論として、core の単体機能はよくテストされており、全テストとプロダクション
ビルドは成功する。一方、v0.7 以降に追加された複数 geometry、外部 palette、
外部 animation、ファイル横断 part reuse が経路ごとに別々に実装されているため、
仕様上 valid なパッケージが CLI で読めない、lint が壊れた参照を正常と判定する、
エディタのファイル操作後に保存先がずれる、といった統合上の問題が残っている。

本監査ではコード変更を行っていない。監査開始時から存在していた未追跡の
`models/wolf-test/` はユーザー作業として扱い、検証・変更・コミット対象から除外した。

## 2. 検証結果

- `npm test` (`ts/`): 27 test files、486 tests passed
- `npm run build` (`ts/`): core と editor の両方が成功
- editor production bundle: JavaScript 1,285.20 kB、gzip 362.33 kB
  - Vite の 500 kB chunk-size warning あり
- tracked model 全件へ `cuboidy-lint --strict` を実行
  - `models/boy-mini` と `models/girl-mini` は W06 により exit 1
  - それ以外は error/warning なし（hint のみのモデルは exit 0）
- `npm pack --dry-run --json` で `@cuboidy/core` の公開内容を確認

## 3. 主要な問題

### A-1. [重大] 検査 CLI が v0.8 の複数 geometry / 外部 palette を扱えない

仕様 §6.9/§6.10 は、manifest の `geometry` リストとモデル全体の外部
`palette` binding を正式機能としている。しかし `cuboidy-view`、
`cuboidy-query`、`cuboidy-snap` が共有する `loadAndAssemble()` は、
`cuboidy.json` と `voxels.cvox` の2ファイルをハードコードして読む。

根拠:

- `ts/packages/core/src/cli/assemble.ts:61-99`
  - `voxels.cvox` を固定で読み、`manifestGeometry()` を使用していない
  - 外部 palette のロードも行っていない
- `ts/packages/core/src/cli/snap-runner.ts:62-65`
  - 常に `asm.cvox.palette` をレンダラーへ渡す

最小再現結果:

1. `geometry: ["body.cvox"]` を持ち、`voxels.cvox` を持たない valid package
   - `loadAndAssemble()` は `voxels.cvox` を読めないとして `exitCode: 2`
2. palette-less `voxels.cvox` と `palette: "palette.json"` を持つ valid package
   - assembly は palette length 0 のまま成功
   - `renderSnapshots()` は `TypeError: Cannot read properties of undefined`

影響:

- README が案内する inspection workflow を、現行仕様の package に適用できない
- lint/editor と view/query/snap で同じモデルの解釈が異なる
- 正常な入力で CLI がユーザー向け診断ではなく例外を出す

推奨:

- manifest、geometry、palette、animation を解決する共通 `ProjectLoader` を core に作る
- lint と inspection CLI と editor が同じ解決層を利用する
- `Assembly` を単一 `cvox`/palette ではなく、解決済み model と effective palette を
  保持する構造へ変更する

### A-2. [重大] ファイル横断 `clone` / `mirror` が解析できない

仕様 §6.9 は、`clone` / `mirror` の参照先をモデル全体で解決し、別 geometry
file の concrete part を参照できると定めている。

一方 `parseCvox()` はファイル単位の parse 完了時に reuse を即時解決する。
そのファイル内に concrete referent が存在しなければ `missing` を返すため、
project layer が後から別ファイルの part を渡す余地がない。

根拠:

- `SPEC.md:304-314`
- `ts/packages/core/src/cvox/parse.ts:124-163`

最小再現:

```text
part hand_r clone hand_l
```

`hand_l` が別の manifest-listed geometry に定義されていても、上のファイル単体の
parse 時点で `part "hand_r" clones unknown part "hand_l"` となる。

推奨:

- `parseCvox()` は unresolved reuse reference を AST に残す
- 全 geometry の concrete part を収集した後、project assembly で一括解決する
- unknown/self/chained/cross-file duplicate の error precedence を project validation
  向けに明文化する

### A-3. [高] 壊れた外部 animation を lint が正常扱いする

`AnimationSchema` の外部参照側は任意の `z.string()` であり、§8 の相対パス、
拡張子、URL/URI 禁止を検証しない。さらに `runLint()` は外部 animation file を
ロードせず、存在・JSON parse・animation schema のいずれも確認しない。

根拠:

- `ts/packages/core/src/animation.ts:53-75`
- `ts/packages/core/src/cli/lint-runner.ts:138-205`
- `SPEC.md:191-225,255-261,811-832`

確認した入力:

```json
{
  "name": "m",
  "parts": [{ "name": "body" }],
  "animations": { "walk": "anims/missing.json" }
}
```

geometry が正常なら `runLint()` は diagnostics 0、exit code 0 を返す。
また `parseManifest()` は次も受理する。

- `"/absolute.txt"` のような不正 animation path
- 負の `duration`
- `"0.0"` から始まらない track
- `duration` より後の time key
- duplicate part name、dangling parent、parent cycle

後半の一部は SPEC §11.5 で planned と明記されているが、lint が成功終了するため、
CI の validity gate としては安全でない。

推奨:

- animation reference に geometry/palette と同じ `refPath('.json')` を適用する
- structural schema と project-level semantic validation を分離する
- lint runner が外部 animation を解決し、missing/parse/schema error を報告する
- time key、duration、hierarchy、duplicate の semantic validator を追加する

### A-4. [高] 公開 JSON Schema が runtime validator より大幅に弱い

生成済み `schema/cuboidy.schema.json` は Zod refine の制約を保持しない。また
Zod tuple から生成された Draft 2020-12 schema は `prefixItems` のみで、配列長を
3に固定していない。

確認結果:

| 入力 | JSON Schema | `parseManifest()` |
|---|---:|---:|
| `position: []` | valid | invalid |
| `position: [1,2,3,4]` | valid | invalid |
| duplicate `geometry` | valid | invalid |
| `geometry: ["/absolute.txt"]` | valid | invalid |

根拠:

- `schema/cuboidy.schema.json:28-37` — path/unique 制約なし
- `schema/cuboidy.schema.json:78-91` — tuple の長さ制約なし
- `ts/packages/core/src/json-schema.ts:39-51`

影響:

- エディタや他言語実装が Schema-valid な manifest を生成しても、TS runtime が拒否する
- 「共通 Schema」による相互運用保証が成立しない

推奨:

- generator の post-process で tuple に `minItems: 3`, `maxItems: 3` を追加する
- reference path を JSON Schema の `pattern` で可能な範囲まで表現する
- geometry に `uniqueItems: true` を追加する
- parity test を valid fixture だけでなく、runtime-invalid の property-based corpus へ広げる

### A-5. [高] 外部 animation file の rename/delete 後に editor state が壊れる

File tree で外部 animation file を rename すると manifest 内の文字列参照は更新されるが、
`source.externalAnims` の `{ path, anim }` は古い path のまま残る。その後の timeline
編集は `rec.path` に書くため、rename 前のファイルを再作成し、manifest が参照する
rename 後のファイルへ編集が反映されない。

根拠:

- `ts/packages/editor/src/App.tsx:934-1030` — rename と manifest ref 更新
- `ts/packages/editor/src/App.tsx:1662-1694` — animation edit は `rec.path` へ保存

delete はさらに不整合が大きい。外部 animation file を削除しても manifest の参照と
`externalAnims` は残るため、現在の session では clip が動き続け、保存・reload 後に
初めて missing reference になる。削除後に clip を編集すると、削除した path が
暗黙に再作成される。

関連する問題:

- part rename/delete は inline animation track だけを書き換え、string-ref animation
  を意図的に skip する (`App.tsx:1291-1441`)
- 外部 animation が古い part name を保持すると、§6.8 により runtime では黙って
  no-op となり、ユーザーが破損に気づきにくい
- external animation file は rename 時に `.json` extension を強制されず、invalid ref
  を editor 自身が生成できる

推奨:

- file CRUD 後は個別 field patch ではなく `resolveProjectRefs()` を必ず再実行する
- external animation の path rename/delete を manifest、files、externalAnims、
  parse errors、removedFiles の単一 transaction にする
- part rename/delete は解決済み external animation file も同じ undo transaction で
  rewrite する

### A-6. [高] Debounced reparse と構造編集/Undo の競合で text と AST が乖離する

Source editor は text を即時 history に記録し、AST の更新を300ms debounceする。
parse error state は debounce 後まで更新されないため、その間は part/palette/manifest
の構造編集ボタンが有効なままである。

構造編集は pending reparse をキャンセルし、最後に成功した古い AST を serialize する。
したがって、source typing 直後に構造編集すると、直前の入力を古い AST で上書きできる。

根拠:

- `ts/packages/editor/src/App.tsx:337-377` — primary cvox text/reparse
- `ts/packages/editor/src/App.tsx:1117-1138` — pending parse を cancel して AST serialize
- `ts/packages/editor/src/App.tsx:1470-1545` — manifest も同じ構造

non-primary file には別の問題がある。

- `cancelAllFileReparse()` は定義されているが使用されていない (`App.tsx:390-395`)
- Undo/Redo は primary cvox と manifest の timer だけを止める (`App.tsx:2129-2157`)
- non-primary file を編集してすぐ Undo すると、Undo 後に古い timer が発火し、
  restored text と post-edit AST が混在し得る

推奨:

- debounce task に document revision/token を持たせ、発火時に current text/revision と
  一致しなければ破棄する
- source text が未解析の間は構造編集を一時停止するか、操作直前に同期 parse する
- load/reset/undo/redo/rename/delete ですべての per-file timer を cancel する
- text と AST を別々に amend する設計を、`ParsedDocument { text, parseState, ast? }`
  の単一 state へ寄せる

### A-7. [中] `loop: false` の animation も editor では永久 loop する

`useAnimationSession()` の rAF clock は animation の `loop` を参照せず、常に
`next % duration` 相当の計算で time を wrap する。

根拠:

- `ts/packages/editor/src/lib/useAnimationSession.ts:156-176`

core sampler は non-loop animation を duration へ clamp するが、editor clock が
duration 到達前後に time を0へ戻すため、その挙動を利用できない。

推奨:

- `inline.loop` が true のときだけ wrap する
- false のときは duration で停止し、`playing` も false にする
- loop/non-loop、duration変更中、clip切替の hook test を追加する

### A-8. [中] 静的 Rig view が `pivot.rot` を無視する

仕様 §7.7 では `pivot.rot` が rest pose transform に含まれ、親の回転は child frame
にも作用する。Animation view の `RiggedParts` は quaternion hierarchy でこれを実装するが、
静的 Rig view の `VoxelScene` は `computePartPositions()` の translation だけを適用する。

根拠:

- `SPEC.md:602-620`
- `ts/packages/editor/src/lib/rig.ts:20-65`
- `ts/packages/editor/src/components/VoxelScene.tsx:86-95`
- 正しく rotation を適用する対照実装:
  `ts/packages/editor/src/components/RiggedParts.tsx:86-145`

影響:

- 同じモデルでも Rig view と Anim view の時刻0/rest pose が一致しない
- rotated parent の child placement が view 間で異なる
- camera framing も未回転 bbox を基準にする

推奨:

- static rig も `RiggedParts` を `poses = null` で利用し、transform 実装を一本化する
- rest pose parity test を追加する

## 4. 設計・品質上の問題

### D-1. Editor の automated test が存在しない

486件の test はすべて `@cuboidy/core` にあり、editor package には Vitest、React Testing
Library、Playwright 等の test script/config/file がない。

特に未検証なのは次の high-risk workflow である。

- text edit → debounced parse → structure edit → undo/redo
- geometry/palette/animation file CRUD と参照追随
- inline/external animation の相互変換
- loop/non-loop playback
- multi-cvox part move と palette remap
- save/export/reload round trip

### D-2. W06 は実際の幾何対称性を判定していない

W06 は `<x>-l` / `<x>-r` の manifest position が `lx === -rx` かだけを見る。
しかし voxel cube の範囲、part size、pivot、mirror relationship によっては、pivot position
が符号反転でなくても geometry volume は対称になり得る。

現に tracked example の `boy-mini` と `girl-mini` は、左右 leg が視覚上対称な
`[-1, 0]` と `[0, 1]` の voxel range を作るが、position `-1` / `0` のため W06 となり、
推奨 authoring workflow の `cuboidy-lint --strict` が exit 1 になる。

推奨:

- W06 を `mirror` relationship が明確な pair に限定する、または
- pivot/size/occupied bbox を world transform して幾何対称性を検査する

### D-3. Socket は package 内で利用関係を表現できない

Socket の position/orientation と attachment 時の座標系は仕様化されているが、manifest に
「どの asset を、どの part のどの socket へ attach するか」という field がない。
したがって現状の socket は外部 runtime 用 metadata であり、`models/crown` を
`models/wolf` の `head:hat` へ attach する関係を Cuboidy package 自体では保存できない。

仕様の設計目標として attachment を含めるなら、asset reference、host part/socket、
missing socket behavior、animation inheritance、palette/material scope を定義する必要がある。

### D-4. `.cuboidy` ZIP 実装が仕様より先行している

SPEC §13 は packed format を v0.8 の out-of-scope としているが、editor はすでに
`.cuboidy` の load/export を行う。現在の loader は `.cvox/.json/.md/.txt` だけを保持し、
binary asset を捨てる。また top-level folder を heuristic により strip する。

仕様化前に少なくとも次を固定する必要がある。

- archive root と `cuboidy.json` の位置
- duplicate/normalized path collision の扱い
- `..`、absolute path、backslash の扱い
- binary/unknown file の round-trip 方針
- compression method、uncompressed size/file count 上限
- UTF-8/BOM validation

### D-5. Documentation が実装と大きくずれている

- root README の file table は JSON Schema と lint を「planned」とするが、roadmap は完了扱い
- root README は core test を473件とするが、現在は486件
- editor README は viewer-only / no manifest / no edit / no save / no animation と説明するが、
  現在の実装はこれらを持つ
- `@cuboidy/core` package description も serializer/full validation を in progress とする

このずれは、未実装範囲や安定性に対する利用者の期待を誤らせ、今回のような project-level
feature gap を見つけにくくする。

### D-6. Package build が `dist/` を clean しない

`npm pack --dry-run` では、現在の `src/` に対応物がない次の stale artifact が含まれた。

- `dist/cvox/classify.js`
- `dist/cvox/layer.js`

`tsc` は削除済み source の output を消さないためである。package `files` が `dist` 全体を
含む以上、build 前に `dist` を clean する必要がある。

## 5. 推奨修正順

1. **Project loading を一本化する**
   - manifest → geometry/palette/animation → reuse resolution → validation を core の共通層へ
   - lint/view/query/snap/editor が同じ結果型を使う
2. **Manifest validator と JSON Schema の parity を確立する**
   - hierarchy、animation、path、tuple、unique constraint
   - valid/invalid project fixtures を cross-implementation contract に追加
3. **Editor の document transaction を安定化する**
   - revision-aware debounce
   - file CRUD 後の全面 re-resolve
   - external animation を含む rename/delete transaction
4. **Rendering semantics を統一する**
   - static/animated rig で同じ transform tree を使用
   - non-loop playback を修正
5. **Editor integration test を追加する**
   - 上記の再現ケースを優先して固定
6. **仕様と documentation を現状へ同期する**
   - packed/socket/alpha の scope を明確化
   - README、package metadata、roadmap の完了状態を更新

## 6. 完了条件の提案

次をすべて満たした時点で、v0.8 project support を「実装済み」と表現できる。

- 同じ valid multi-file fixture を lint/view/query/snap/editor がすべてロードできる
- external palette fixture を `cuboidy-snap` が例外なく描画できる
- cross-file clone/mirror fixture が parse/serialize/reload できる
- missing/invalid external animation で lint が exit 1 になる
- JSON Schema と `parseManifest()` の fixture parity が成立する
- external animation file rename/delete と part rename/delete が1 undoで整合する
- source typing 中の undo/structure edit で text/AST divergence が起きない
- `loop: false` が終端で停止する
- Rig/Anim の rest pose が `pivot.rot` を含めて一致する
- editor の上記 workflow に automated regression test がある
